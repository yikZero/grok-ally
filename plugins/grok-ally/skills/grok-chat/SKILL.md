---
name: grok-chat
description: Use when the user asks to talk to Grok, ask Grok for a second opinion, continue a Grok conversation, or use Cursor Agent through Grok Ally from Codex or Claude Code.
---

Use this plugin's `grok_chat` tool. Always pass the user's absolute project directory as `cwd`; never use the plugin install/cache directory.

- Choose `provider: "cursor"` when the user requests Cursor usage; its default is `cursor-grok-4.6-xhigh`. Otherwise follow the configured backend (`GROK_ALLY_PROVIDER`, default Grok). Do not switch providers automatically on quota/auth failures. Keep the complete returned handle; it binds the backend and, for Cursor, the model. Cursor resumes infer the backend even when omitted.
- Start a conversation by omitting `sessionId`. Keep the returned `sessionId` in this conversation and pass it for follow-ups. Do not borrow an ID from an unrelated conversation or silently start over when loading fails.
- Only send the user's requested prompt and relevant context. Do not read or export host transcript files, hidden reasoning, system/developer instructions, or credentials. Ask before sharing unrelated private context.
- Leave `write=false` for discussion, research, and review. Use `write=true` only when the user has authorized Grok to modify the workspace. Grok enables its workspace sandbox. Cursor uses verified Ask/Agent modes and one-time approvals; these are not the same OS-level restriction. Native tools, hooks, and remote tools remain governed by the selected service’s configuration.
- `starting`, `running`, and `cancelling` are not finished. Normally poll `grok_status` with only `requestId` and `waitSeconds=25`; it waits for completion and returns compact progress at the deadline. Omit `afterRevision` during ordinary waits: that cursor returns on progress and can increase host calls.
- For a progress investigation, use `detail=full`, `waitSeconds=0`; add `afterRevision` set to the last returned `revision` only when early progress returns are useful. Full-mode tool updates are incremental when a revision is supplied. Show running text as partial.
- To inspect each retained tool's latest outcome, use `grok_status` with `requestId`, `detail=full`, and `waitSeconds=0`, without `afterRevision` or paging parameters. `tools` is already merged by ID; read history only for earlier transitions or tools removed from the recent list.
- Terminal `text` is a recent preview and can include intermediate assistant updates. If `truncated=true`, read earlier pages when needed to answer the user's question; read all pages if the user requires the complete answer. Start at `outputOffset=0` or pass `outputLimit` alone, then use `output.nextOffset` while `output.hasMore=true`. For a finished turn, stop paging when `output.hasMore=false` even if `truncated=true`: that page may omit earlier text. Do not present an excerpt as the full answer. Save needed output before disconnecting; pagination is local to this MCP process.
- `status` is the selected agent's turn. `toolSummary.state` is `active`, `unconfirmed`, or `confirmed` for observed tools (`confirmed` includes failures and is not independent validation). Compact terminal replies may list up to three `unconfirmedTools` and `latestFailure`. `dropped` means removed from the recent view, not missing execution. Page sanitized history with `toolOffset`/`toolLimit` (limit alone starts at 0; pages also stop at 16,000 bytes). Do not mix those with output paging. `recovery` stays `unknown` unless that same tool ID later completed.
- For substantial work, state the target files, acceptance conditions, and a useful stopping point. Use recent tools, durations, and `lastProgressAt` to assess progress; an unchanged revision alone does not prove a stall. If the task is stuck or should be narrowed, cancel, follow the cleanup guidance below, then reuse the `sessionId` (it loads a fresh native process) to summarize or continue with a smaller scope. `toolSummary.state` `unconfirmed` means the bridge did not receive a final tool outcome; it does not prove the tool is still running. Do not treat `completed` as host acceptance or as an OS-process exit.
- If the request ID is missing, call `grok_status` with the exact workspace `cwd` instead. It lists active and recent requests in this MCP process. Select the relevant ID before reading or cancelling; do not guess another conversation's ID. A restart clears this list.
- `incomplete` (including turn limits), `failed`, and `cancelled` are not successful completion. Preserve partial output and the session ID, and report the actual status.
- Attribute the answer to the selected backend/model. Preserve its evidence, uncertainty, file locations, and proposed next steps; distinguish any host verification or conclusions from Grok's report. Do not substitute a host-generated answer for a failed Grok call.
- To stop, call `grok_cancel`, then poll `grok_status` until the request is terminal; `cancelling` is still pending, and an error may end as `failed`. A native `cancelled` stop uses the same cleanup. `cleanup.state` (`pending`/`confirmed`/`unconfirmed`) reports observed local process cleanup and is not `toolSummary.state`. If cleanup is unconfirmed, inspect the reason and any remaining processes before starting overlapping commands; polling a terminal result will not retry cleanup. Then reuse the `sessionId`; the next turn loads a new native process. Cancellation does not undo edits.
- For Grok, omit `model` and `effort` to use native settings. For Cursor, omit both for the fixed xhigh default; do not pass separate `effort`. Other models require ACP IDs/parameters. Cursor persists model choices in its native config; Ally handles restore the original model on reload. They are creation-only options. Keep `cwd` and `write` consistent for a live session. Do not pass `maxTurns`; Grok's ACP mode does not enforce that CLI option.
- When sharing an ID with another local MCP client, finish the active turn first. Do not prompt the same Grok session from two host processes concurrently.
- `grok_setup` checks installation for the selected provider, not login. Authentication errors require `grok login` or Cursor Agent login (`agent login`, or the executable from `CURSOR_BINARY`). Cursor interactive questions/plans are returned to the host rather than answered automatically.
